# Project Desk — поддержка AI Challenge App

Отдельное Go-приложение: CRM, пользователи, тикеты, чат по проекту и ответы DeepSeek с проверяемыми цитатами. Собственный процесс и SQLite; исходный `ai-challenge-app` запускается независимо.

## Схема

```text
Браузер → SSH-туннель / HTTPS → Support CRM (VPS, :8090) → DeepSeek API
                     ├→ CRM MCP → SQLite
                     └→ Project MCP (Mac, :8091) → существующий RAG + README/docs/код
```

Генерация выполняется только через DeepSeek. CRM MCP и SQLite находятся на VPS. Эмбеддинги нужны для поиска и остаются в существующем RAG проекта на Mac (`embeddinggemma`). Windows может использоваться как клиент с SSH-туннелем; для демонстрации с Mac он не нужен.

Project MCP — отдельная команда `cmd/supportmcp` в репозитории `ai-challenge-app`. Она использует существующие `internal/rag` и `internal/ragindex`, проверяет актуальность исходных файлов и работает при остановленном основном веб-приложении. Если Mac или MCP недоступен, CRM продолжает работать, но ассистент сообщает, что документы не получены.

Исходники и инструкция установки Project MCP включены в [интеграцию с ai-challenge-app](integrations/ai-challenge-app/README.md). Примените патч в основном проекте перед запуском команды ниже. Сам CRM собирается из этого репозитория независимо от основного приложения.

## Запуск сервиса

Нужен Go 1.25+ для сборки. Готовый бинарник CRM не требует Go, SQLite CLI или Ollama; скрипты подготовки и резервного копирования используют Python 3.

```sh
cp .env.example .env
# Заполните DEEPSEEK_API_KEY, SUPPORT_ACCESS_TOKEN и PROJECT_MCP_TOKEN.
# Токены доступа — разные случайные строки не короче 32 символов.
go run .
```

Откройте `http://127.0.0.1:8090` и введите `SUPPORT_ACCESS_TOKEN`. Ключ DeepSeek хранится только на сервере; браузер не получает его. `.env` читается при запуске; непустое окружение процесса имеет приоритет. Файлы данных, секреты, сборки и локальные отчёты исключены из Git.

На Mac в корне `ai-challenge-app`, после установки интеграции:

```sh
export SUPPORT_MCP_TOKEN='тот же токен, что PROJECT_MCP_TOKEN у CRM'
go run ./cmd/supportmcp -root . -addr 127.0.0.1:8091
```

Сетевая схема по умолчанию: оба приложения слушают localhost. Для двух компьютеров используйте SSH-туннель: на Mac создайте reverse forwarding порта Project MCP и forwarding порта CRM:

```sh
ssh -N -o ExitOnForwardFailure=yes \
  -R 127.0.0.1:18091:127.0.0.1:8091 \
  -L 127.0.0.1:8090:127.0.0.1:8090 tunnel-user@vps-host
```

На VPS задайте `PROJECT_MCP_URL=http://127.0.0.1:18091/mcp`. Браузер на Mac открывает CRM по `http://127.0.0.1:8090`. Для Windows нужен отдельный SSH-forward либо доступ через HTTPS. Успешность туннеля и наличие слушающих портов проверяются отдельно. Штатный туннель нужно поддерживать запущенным.

`SUPPORT_EMBEDDING_URL` и `SUPPORT_EMBEDDING_MODEL` на Mac переопределяют адрес эмбеддингов и модель. По умолчанию `http://127.0.0.1:11434` и `embeddinggemma`. Модель должна соответствовать модели существующего индекса. Изменения корпуса требуют штатной переиндексации в исходном проекте.

## Развёртывание и восстановление соединения

`scripts/deploy_windows.py` принимает `--host`, `--user`, `--key` и `--known-hosts`. Он использует существующий проверенный SSH-доступ, переносит только exe, локальную конфигурацию и README в `Apps/ProjectDesk` профиля Windows-пользователя. Сохраняет SQLite при обновлении и регистрирует задачу `ProjectDeskSupport` от этого пользователя с ограниченными правами и запуском при старте Windows. Каталог приложения ограничен текущим пользователем, SYSTEM и администраторами. Логи находятся в `.local/service.log` каталога установки.

`scripts/install_mac_agents.py` принимает те же параметры и `--project-root`. Устанавливает пользовательские LaunchAgents `local.projectdesk.project-mcp` и `local.projectdesk.tunnel`. Они запускаются при входе в macOS и восстанавливаются после завершения процесса или разрыва SSH. Plist-файлы не содержат токенов: MCP-обёртка читает их из локального `.env` при старте. Если изменили токен, обновите конфигурацию на обеих машинах и перезапустите службы. Остановка пользовательских агентов: `launchctl bootout gui/$(id -u)/local.projectdesk.tunnel` и аналогично для `local.projectdesk.project-mcp`.

При использовании прежней установки на Windows оба компьютера должны быть включены для ответов по актуальному RAG. После сна Mac туннель восстанавливается, когда сеть и SSH-сервер снова доступны. Автозапуск локального сервиса эмбеддингов на Mac настраивается отдельно; при его недоступности ассистент явно отмечает прямое чтение документов.

### Перенос только CRM на Linux VPS

Основная схема: браузер → SSH-туннель или HTTPS → CRM на VPS → DeepSeek API.
CRM MCP и SQLite работают на VPS. Project MCP, исходники, RAG и `embeddinggemma`
остаются на Mac; оттуда создаётся обратный SSH-туннель на VPS. Для ответов по проекту
Mac должен быть включён. Перенос CRM не переносит основной `ai-challenge-app`.

Подготовка выполняется локально и не меняет работающий Windows-сервис:

```sh
# Выберите архитектуру VPS: amd64 или arm64.
python3 scripts/prepare_vps.py --arch amd64
```

Приватный каталог `.local/vps/amd64` содержит Linux-бинарник, конфигурацию,
systemd-службу, установщик и пример блока Caddy. Go на VPS не требуется.
В конфигурации отключены демо-данные, CRM слушает только `127.0.0.1:8090`,
MCP ожидается на `127.0.0.1:18091/mcp`. `SUPPORT_SECURE_COOKIES=true` нужен
для входа через HTTPS, когда TLS завершается на reverse proxy. Для временного
доступа только через локальный SSH-forward используйте `--http-tunnel`.
Приватный каталог содержит ключ DeepSeek и токены, его нельзя публиковать.

При окончательном переключении остановите запись в старую CRM, сделайте согласованный
снимок SQLite с Windows и повторите подготовку с `--database /path/to/snapshot.db`.
Установщик импортирует снимок только при отсутствии базы на VPS, а обновления
бинарника сохраняют существующую базу. Подготовка без `--database` исключает снимок
от предыдущего запуска. Резервную копию и старую установку сохраняйте до проверки переноса.

Перед установкой проверьте ОС и архитектуру, свободный порт 8090, существующие
службы и прокси. Для Linux с systemd, `curl` и `useradd`, после передачи приватного
каталога на VPS:

```sh
sudo bash /path/to/bundle/install.sh /path/to/bundle
sudo systemctl status projectdesk.service
```

Приложение запускается от отдельного пользователя `projectdesk`, конфигурация
хранится в `/etc/projectdesk/crm.env` (root, 0600), база — в
`/var/lib/projectdesk/support.db`. Для обновления передайте новый пакет без базы
и повторите установку. Перед изменениями сохраняйте резервные копии конфигурации и базы.
Служба принимает SIGTERM и ждёт завершения HTTP-запросов до закрытия SQLite.

`projectdesk-backup.timer` ежедневно запускает согласованное копирование SQLite
через Python SQLite Backup API. Копии находятся в `/var/lib/projectdesk/backups`,
сохраняются последние 14 снимков. Ручная копия:
`sudo systemctl start projectdesk-backup.service`. Бэкапы на том же VPS помогают
восстановить записи после ошибки, но для восстановления при потере VPS нужна
отдельная копия за пределами сервера.

Для первоначальной проверки, сохранив туннель Windows и его Mac-порт 8090:

```sh
python3 scripts/start_tunnel.py --target your-vps-ssh-alias --local-port 18090
```

Браузер на Mac открывает `http://127.0.0.1:18090` (сборка `--http-tunnel`).
Для доступа по домену объедините блок из `deploy/vps/Caddyfile.example` с
существующей конфигурацией reverse proxy. [Caddy](https://caddyserver.com/docs/automatic-https)
получает и обновляет сертификат при корректной DNS-записи и доступных портах 80/443.
Порты CRM, MCP и Ollama остаются внутренними.
После проверки через HTTPS используйте `--local-port 0`: останется только обратный
туннель MCP. Его автозапуск на Mac переключается на VPS после успешной проверки.
Windows-службу и старый туннель останавливают после проверки данных и ответа с журналом MCP.

Для постоянного подключения Mac без перезапуска уже работающего Project MCP:

```sh
python3 scripts/install_mac_agents.py --project-root /path/to/ai-challenge-app \
  --target tunnel-user@vps-host --key /path/to/tunnel-key \
  --known-hosts /path/to/verified-known-hosts --local-port 8090 --tunnel-only
```

Используйте отдельный SSH-аккаунт для туннеля с разрешением слушать только
`127.0.0.1:18091` на VPS и подключаться только к `127.0.0.1:8090`.
Автозапускаемый туннель не требует административного SSH-ключа.
В этой схеме адрес `http://127.0.0.1:8090` работает на Mac, где запущен forwarding.
На другом компьютере нужен собственный SSH-forward либо отдельный доступ по HTTPS.

На Windows в режиме VPS работает SSH-клиент, а прежняя задача `ProjectDeskSupport`
отключена. Задача `ProjectDeskVPSAccess` запускается при старте Windows и выполняет
`scripts/start_windows_vps_client.ps1` с отдельным ключом и закреплёнными ключами
хоста VPS. На целевом ПК скрипт установлен в `.local/vps-client/run.ps1` каталога
ProjectDesk. Скрипт восстанавливает соединение после разрыва и слушает только
`127.0.0.1:8090`; браузер открывает по этому адресу CRM на VPS.
Ключ Windows создан на Windows и не переносится на Mac. На VPS у него ограниченный
доступ к туннелю без удалённой оболочки. Лог соединения —
`.local/vps-client/ssh-client.log`. Исходная Windows-база и её резервная копия
сохраняются для отката.

Проверка на Windows:

```powershell
Get-ScheduledTask -TaskName ProjectDeskVPSAccess,ProjectDeskSupport
Get-NetTCPConnection -LocalPort 8090 -State Listen
# Портом 8090 владеет ssh.exe; процесс support-crm.exe работает на VPS.
```

## CRM и ответы

- Пользователи: имя и окружение; создание через интерфейс.
- Тикеты: пользователь, тема, описание, категория, приоритет, окружение, диагностический контекст.
- Статусы: открыто → в работе → решено; меняются явным действием оператора.
- В карточке рядом со статусом есть «Удалить обращение». После подтверждения удаляются тикет, вся его переписка, источники и журналы MCP; пользователь и другие обращения сохраняются. Отмена оставляет карточку и черновик без изменений. Во время подготовки ответа удаление заблокировано.
- Переписка и заметки оператора сохраняются в SQLite. Истории разных тикетов разделены.
- Вопрос по проекту без тикета — отдельный запрос по базе знаний. Общий чат хранится только в открытой вкладке; вопросы там независимы. Для продолжительного контекстного обсуждения создайте тикет.
- Ассистент читает тикет и пользователя через настоящий MCP SDK. CRM MCP соединён с ассистентом in-memory; Project MCP — по Streamable HTTP с Bearer-токеном.
- Каждый факт ответа содержит ID источника и точную цитату. Неверный JSON или цитаты допускают одну повторную генерацию. Непроверенный ответ не показывается. Совпадение цитаты проверяется программно; логическое соответствие вывода источнику оценивается отдельно.
- Под каждым новым ответом есть «Журнал MCP»: хронологический список инструментов CRM и проекта, аргументы, фактические результаты, ошибки, время начала и длительность. Записи создаются клиентом MCP при выполнении, а не моделью. Журнал тикета сохраняется с ответом и доступен после обновления страницы. Для старых ответов, полученных до этой функции, показана отметка об отсутствии записи.
- В журнале также виден «Контекст, подготовленный для DeepSeek»: ID тикета, число предыдущих сообщений пользователя/оператора и точный список источников, включённых в запрос модели. Источники в самом ответе отдельно показывают, какие цитаты модель использовала.
- Служебные токены и ключи из конфигурации маскируются. Вложенные журналы прошлых ответов исключены; превью аргументов и результата ограничено 64 КиБ с явной отметкой и исходным размером. Сами журналы не добавляются в контекст модели. Ошибка поиска и последующее прямое чтение документов остаются отдельными вызовами в журнале.
- Если RAG не работает или ничего не нашёл, используется явно помеченное чтение базовых документов через MCP. Оно не выдаётся за успешный поиск по индексу.
- Модель не получает инструментов записи CRM, запуска команд или произвольного чтения файлов. Запись выполняет сервис по действиям пользователя.

Интерфейс рассчитан на частную CRM одного оператора с токеном доступа. Пользователи CRM — записи о пользователях продукта, а не отдельные учётные записи доступа к этой панели.

## Демонстрация действующей установки на VPS

На настроенном Mac выполните `python3 scripts/show_vps_status.py`.
Команда использует приватную конфигурацию текущего развёртывания из `.local`,
подключается к VPS и выводит hostname, Linux, состояние и PID systemd-службы,
готовность MCP и RAG, число записей SQLite и состояние резервного копирования.
Она выполняет только чтение и не выводит значения ключей или токенов.

В браузере откройте `http://127.0.0.1:8090`. Для вопросов о проекте без сохранения
обращения используйте «Спросить о проекте». Обращение создаётся при реальном
вопросе поддержки, когда нужны отдельная история, данные пользователя и статус.
Автоматически добавлять примеры для демонстрации не требуется.

1. В реальном обращении опишите вопрос, окружение и уже выполненные действия, затем задайте вопрос ассистенту.
2. Под ответом раскройте «Источники и точные цитаты»: документация и данные обращения помечаются отдельно.
3. Раскройте «Журнал MCP»: `crm_get_ticket` и `crm_get_user` читают контекст, `project_search_docs` выполняет RAG, `crm_add_message` сохраняет вопрос и ответ. В каждом вызове доступны реальные аргументы и результат.
4. В «Контекст, подготовленный для DeepSeek» покажите ID тикета, предыдущие сообщения и переданные источники.
5. Обновите страницу: переписка, источники и журнал тикета сохранятся в SQLite на VPS.

Для нового вопроса по знаниям без тикета используйте «Спросить о проекте»,
например «Как устроены RAG и проверка цитат?». Общий чат хранится только во вкладке.
Windows можно выключить при демонстрации с Mac; VPS, Mac, Project MCP, эмбеддинги
и туннель Mac должны оставаться доступны.

## Демонстрационные обращения

На пустой базе при `SUPPORT_SEED_DEMO=true` импортируются шесть обращений из `fixtures/tickets.json`. Они явно помечены «ДЕМО» и описывают функции реального проекта. Они не утверждают, что соответствующая неисправность существует сейчас.

| ID | Проверяемый сценарий |
|---|---|
| SUP-001 | Разделение локальной и удалённой Ollama |
| SUP-002 | Устаревший RAG-индекс после изменения документации |
| SUP-003 | HTTP 504 от DeepSeek и влияние maxTokens |
| SUP-004 | Sliding Window и сохранённый архив истории |
| SUP-005 | Документы найдены, но invalid_evidence |
| SUP-006 | MCP-каталог доступен, авторизация GitHub не прошла |

Повторный запуск не сбрасывает существующие обращения. Новые тикеты не имеют метки «ДЕМО».

## API

Авторизация: HttpOnly SameSite Strict cookie после `POST /api/login` или `Authorization: Bearer SUPPORT_ACCESS_TOKEN` для серверной диагностики.

| Метод и путь | Назначение |
|---|---|
| `GET /healthz` | Процесс доступен; не доказывает готовность зависимостей |
| `GET /api/status` | Состояние Project MCP, индекса и наличие ключа DeepSeek |
| `GET/POST /api/users` | Список и создание пользователей |
| `GET/POST /api/tickets` | Список и создание обращений |
| `GET /api/tickets/{id}` | Обращение и его переписка |
| `PATCH /api/tickets/{id}` | Изменение статуса |
| `DELETE /api/tickets/{id}` | Удаление обращения и его переписки через CRM MCP; 409 при активном ответе, 404 если обращения нет |
| `POST /api/tickets/{id}/notes` | Заметка оператора |
| `POST /api/chat` | `{ "ticketId": "SUP-004", "question": "Почему забыто начало?" }`; ticketId необязателен |

Индикатор DeepSeek подтверждает наличие настройки, а не валидность ключа или доступность API. Это проверяет настоящий запрос. Не включайте секреты в описания тикетов: вопрос, выбранные сообщения и фрагменты документации передаются DeepSeek.

## Проверка и сборка

```sh
go test ./...
go test -race ./...
go vet ./...
node --check web/app.js
go build -o dist/support-crm .
GOOS=windows GOARCH=amd64 CGO_ENABLED=0 go build -trimpath -o dist/support-crm.exe .
```

Тесты проверяют SQLite после повторного открытия, изоляцию тикетов, MCP-протокол, схему создания обращений, отказ при неверных цитатах, fallback документов, недоступность Mac, авторизацию и серверное хранение ключа. Внешний DeepSeek проверяется отдельно живым запросом; тесты провайдера используют подставной HTTP-сервер.

`journal_test.go` дополнительно проверяет фактические результаты MCP (включая вызовы без запрошенного output), ошибки инструментов, сохранение полного журнала с последней записью ответа, изоляцию параллельных запросов, маскирование секретов, ограничение Unicode-превью и журнал перехода от ошибки RAG к чтению документов.

GitHub Actions запускает тесты с детектором гонок, `go vet`, проверку синтаксиса JavaScript, Python и Bash, а также сборки Linux и Windows. Ключ DeepSeek и запущенные внешние сервисы для этих проверок не требуются.
